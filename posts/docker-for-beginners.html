Docker for Beginners: Containers Explained Simply

Docker's promise is simple: the app runs the same on your laptop, on the server and on your teammate's machine. No more "works on my machine". The mechanism behind that promise is a container — a lightweight, isolated process with everything it needs bundled around it.

Container vs virtual machine

A virtual machine emulates a whole computer — gigabytes, slow to start. A container shares your host OS kernel and packages only the app plus its libraries. That makes containers small (megabytes) and fast (seconds). Ten containers idle on a laptop that would struggle with three VMs.

Install and run your first container

Install Docker Desktop (Windows/Mac) or docker-ce (Linux), then:

docker run --rm -it hello-world
docker run --rm -p 8080:80 nginx

Second command: pull the official nginx web server, start it, and map port 80 inside the container to 8080 on your machine. Open localhost:8080 — you are running a web server without installing a single nginx file on your system.

The five commands you will type daily

docker ps                 # running containers
docker logs -f <name>     # follow a container's output
docker stop <name>        # stop it
docker images             # what do I have locally?
docker exec -it <name> sh # shell inside the container

That last one is the superpower: a shell straight into a known-good environment, no matter what state your host is in.

Building your own image

An image is the snapshot a container starts from. You build one with a Dockerfile:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Then build and run it:

docker build -t myapp .
docker run --rm -p 9000:9000 myapp

Read the file top to bottom: start from an official Python image, set a folder, copy the requirements, install them, copy the code, define the start command. Layer order matters — changing app code should not rebuild your dependencies, so copy requirements first.

One command for a whole stack

When your app needs a database and a cache too, use docker compose with a docker-compose.yml:

services:
  web:
    build: .
    ports:
      - "9000:9000"
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev

docker compose up starts both, networked and ready; docker compose down tears everything down. This file doubles as documentation anyone can run with one command.

When not to use Docker

One-off scripts, GUI apps, and tiny static sites usually do not need it. Containers shine when you have services to coordinate, dependencies to pin, or environments to reproduce. If your next step is automating builds of those images, they slot directly into GitHub Actions.
